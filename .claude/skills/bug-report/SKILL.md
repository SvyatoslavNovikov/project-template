# bug-report

Баг — тикет в `docs/requirements/bugs/`, не узел дерева эпик → стори и не строка результата прогона. Правила — `docs/requirements/README.md` и `TRACEABILITY.md`, шаблон — `docs/requirements/_templates/bug.md`.

## Сначала проверить, что это баг

- Система ведёт себя не так, как сказано в SR, NFR или критериях приёмки стори — баг.
- Требования нет или оно молчит о таком случае — это не баг, а новая стори или правка требования. Сказать пользователю и не заводить баг.
- Похожий баг уже есть: Grep по `docs/requirements/bugs/` (симптом, экран, `defects` на то же требование). Есть открытый — дополнить его, а не плодить дубль.

## Файл

1. ID — **Next** из `docs/requirements/_registry.md`, после создания сдвинуть реестр. Имя `PRJ-<n>-bug-<slug>.md`, slug латиницей через дефисы.
2. `title` — `<экран или компонент> — <симптом>`: без «не работает», без истории поиска, один симптом. Несколько проблем — несколько багов.
3. Поля:
   - `severity` — `blocker` | `major` | `minor` | `trivial`. Не очевидно — спросить пользователя.
   - `environment` — ключ из `_catalogs/environments.md`, где воспроизвели.
   - `affects_releases` — ключи из `_catalogs/releases.md`, на которых воспроизвели. `releases` (куда чиним) при заведении не заполнять: это решение о версии.
   - `defects` — SR или NFR, которое ломается. Не нашёлся — `TBD` и вопрос пользователю, требование не угадывать по словам симптома.
   - `found_in` / `found_on` — прогон и кейс, если баг найден в прогоне; иначе пусто.
   - `status: open`, `parent` пустой.
4. Тело по шаблону:
   - **Воспроизведение** — точные шаги, контролы по названию в интерфейсе, тестовые данные без паролей и токенов.
   - **Фактический результат** — что видно, текст ошибки дословно.
   - **Ожидаемый результат** — со ссылкой на требование (`PRJ-<n>`) или критерий приёмки.
   - Вложения — только реальные скриншоты и логи со стенда. Логи без токенов и персональных данных.

## Если баг найден в прогоне

- В файле прогона `docs/tests/runs/…` у строки `results` этого кейса заполнить `defect: PRJ-<n>`: по `TRACEABILITY.md` после заведения бага строка обязана на него ссылаться.
- Повторный прогон, который ловит тот же баг, ссылается на него же; `found_in` / `found_on` бага не меняются (это первое обнаружение).

## Проверка

`python .claude/hooks/docs_lint.py <файл бага> docs/requirements/_registry.md` и, если правился прогон, его файл.

## Не делать

- Не заполнять `releases` (Fix Version) и не менять статус бага дальше `open` без решения пользователя.
- Не заводить баг во внешнем трекере: это отдельный шаг по команде пользователя, если в проекте подключена интеграция (`optional/`).
- Не выдавать предположение о причине за факт: техническая гипотеза — отдельным абзацем с пометкой «гипотеза» или не писать вовсе.
