# regression-report

Прогон — событие, а не спецификация: он фиксирует, чем кончились кейсы на конкретной сборке и окружении. Правила — раздел «Как добавить прогон» в `docs/tests/README.md` и «Слой 3» в `docs/requirements/TRACEABILITY.md`, шаблоны — `docs/tests/_templates/test-run.md` и `test-result.md`.

## Когда прогон идёт в репозиторий

- Приёмка истории, сертификация релиза, ручной регресс — да.
- Массовые CI-результаты — нет: в git только схема и редкие ручные или выборочные прогоны. Автоматический прогон оформлять, только если пользователь просит (обычно — сертифицирующий релиз).

## Порядок

1. **Сьюит.** Прогон исполняет сьюит (`executes` → `PRJ-T-<n>` сьюита). Нужного сьюита нет — предложить пользователю завести его (`docs/tests/suites/`, связь `contains` на кейсы), а не прогонять кейсы «вне сьюита».
2. **Номер и папка.** **Next** из `docs/tests/_registry.md`, после создания сдвинуть реестр. Папка `docs/tests/runs/PRJ-T-<n>-tr-<slug>/`, в ней файл с тем же именем по шаблону.
3. **Шапка.**
   - `mode` — `manual` или `automated`; `executor` — кто прогонял.
   - `environment` — ключ из `_catalogs/environments.md`; `release` — ключ из `_catalogs/releases.md`, только если прогон сертифицирует поставку.
   - `build` — сборка продукта; `revision` — commit этого репозитория на старте (`git rev-parse --short HEAD`), обязателен с `in-progress`.
   - `started`, `finished`.
4. **Состав.** `results` — снимок кейсов сьюита на момент старта, у каждого `status: not-run`. Сьюит изменился после старта — не править состав, а заводить новый прогон.
5. **Результаты.** По ходу менять `results[].status`: `passed` | `failed` | `blocked` | `skipped` | `not-run`. Короткий комментарий — в `comment`. Длинный разбор падения — `results/PRJ-T-<кейс>.md` по шаблону `test-result.md`.
6. **Дефекты.** На `failed` / `blocked` — баг через скилл `bug-report` и `defect: PRJ-<n>` в строке. До заведения бага пустой `defect` допустим.
7. **Завершение.** `status: completed` (или `aborted`), `outcome` по правилу: есть `failed` → `failed`; иначе есть `blocked` → `blocked`; иначе нет `not-run` → `passed`. Таблица «Результаты» в теле совпадает с `results`.

## Результаты автоматического прогона

Брать из отчёта раннера (JSON Playwright и т.п.), а не переписывать по памяти. Статусы переводить так же, как в агенте `playwright-runner`: `passed` → `passed`, `failed` и `timedOut` → `failed`, `skipped` → `skipped`, недоступный стенд → `blocked`, кейс без автотеста → `not-run`. Скриншоты и сырой отчёт — ссылками на `tmp/agents/…` или на вложения, которые укажет пользователь; в `docs/` не копировать.

## Проверка

`python .claude/hooks/docs_lint.py docs/tests/runs/<папка прогона> docs/tests/_registry.md`: состав, статусы, `revision`, `outcome`, ссылки на баги.

## Не делать

- Не копировать шаги кейсов в прогон: только ID и статус, иначе тексты разойдутся.
- Не удалять и не переписывать прошлые прогоны: новый результат — новый прогон.
- Не ставить `passed` без реального прогона: не проверялось — `not-run` или `skipped` с причиной в `comment`.
- Не менять статусы кейсов (`automated` и т.п.) и требований по итогам прогона без решения пользователя.
