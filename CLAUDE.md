# PRJ: правила для Claude Code

`PRJ` — заглушка кода проекта, заменить вместе с остальными (см. [README.md](README.md)).

## Карта
- [context.md](context.md) — карта инструкций и правила работы над продуктом: прочитать перед работой с требованиями и тестами.
- `docs/requirements/`, `docs/tests/` — требования и тесты по шаблонам из `_templates/`.
- [.claude/toolkit.md](.claude/toolkit.md) — скиллы, агенты, хуки и их настройка. `docs/handoff/` — передача работы между сессиями (скилл `handoff`). `docs/meetings/` — конспекты встреч (скилл `meeting-notes`).
- `tmp/agents/` — сырые результаты исполнителей, в git не попадают.

## Личные правила: CLAUDE.local.md
Личное (кто работает, машина, доступы, предпочтения) — в `CLAUDE.local.md` в корне. Он в `.gitignore`, у каждого человека и на каждой машине свой. Если файла нет, хук `SessionStart` напомнит: предложить пользователю создать его по `.claude/claude-local.template.md`, недостающее спросить, не придумывать. Правила, нужные агентам и коллегам, в `CLAUDE.local.md` не класть: только сюда.

## Жёсткие правила
- Ничего не создавать и не менять во внешних системах (трекеры, вики, TMS, макеты, общие окружения) без прямой команды пользователя. Сначала показать, что именно будет сделано (dry-run, список изменений). Хук `external_write_guard` дополнительно спрашивает подтверждение на запись в системы из `.claude/hooks/config.json`: это не замена команде пользователя.
- Токены брать только из окружения: не печатать, не вставлять в файлы и команды, не выводить файлы настроек с блоком `env`.
- Решения уровня эпика и стори и NFR пользователя (его условия на реализацию) принимает пользователь; открытые вопросы этого уровня закрывать и удалять только по его слову. Системный уровень (SR, остальные NFR, ADR) решает основной поток после независимого ревью, решение опирается на стори, эпик и NFR пользователя и не противоречит им. Кто какой статус переводит — `docs/requirements/README.md`, «Кто переводит статус».
- Чего нет в источниках — `TBD` или вопрос, а не «логичное» допущение.
- Чужие репозитории: `git -C <путь>` вместо `cd`.
- `docs/requirements/_canceled/` — отменённые требования: не читать, не искать в них и не ссылаться на них, если пользователь прямо не попросил. Агентам — то же (правило в их файлах). Как отменять — `docs/requirements/README.md`, «Отменённые требования».
- Файлы сохранять с LF. Сообщение коммита с кириллицей из PowerShell писать в файл и коммитить через `git commit -F`.

## Оркестрация и экономия токенов
Расход определяют длина контекста и число шагов: около 70% уходит на перечитывание накопленного контекста. Поэтому основной поток держим коротким.
- Основной поток ведёт диалог, принимает решения вместе с пользователем, пишет финальные тексты и делает всё необратимое (коммиты, push, деплой, запись во внешние системы).
- Тяжёлое чтение выносить в агентов с чистым контекстом: широкий поиск по коду, длинные логи и вывод тестов, макеты, сырые выгрузки, длинные стенограммы, сверку требований с кодом, пакеты однотипных требований или кейсов. Исследовательские задачи — во встроенный `Explore` или `general-purpose`. Порог: задача на 4+ шага или с сырым выводом больше 10K токенов, если контекст основного потока уже больше 100K. В свежей сессии мелочь делать самому.
- Эксперименты в браузере (воспроизвести баг, проверить поведение страницы, прочитать макет) — агенту, а не в основном потоке: он возвращает шаги, наблюдения и результат одним дайджестом. Ожидание дольше минуты (сборка, долгие тесты, таймауты) — внутри агента или фоновой задачей, не блокирующим `sleep` в основном потоке.
- Исполнитель пишет результат в файл (`tmp/agents/<тема>/…` для сырых данных, `docs/…` для требований и кейсов) и возвращает дайджест до 15 строк с источниками. Любой факт со ссылкой (`PRJ-<n>`, `PRJ-T-<n>`, ключ внешней задачи, ссылка на макет, `путь:строка`), иначе `TBD`.
- Бриф агенту: цель, входные файлы по путям, ограничения, формат результата, что не делать (не коммитить, не писать во внешние системы, не закрывать вопросы, не менять каркас хранения требований, не угадывать), потолок объёма («без доработок сверх задачи») и число шагов. Агент не видит историю чата и память: всё нужное в брифе или в этом файле. Параллельным исполнителям отдавать непересекающиеся файлы.
- Агенты проекта перечислены в `.claude/toolkit.md`. Агента проекта запускать его типом. Если типа нет в списке доступных агентов, не подменять его молча на `general-purpose`: сказать пользователю и проверить заголовок `python .claude/hooks/frontmatter_lint.py`. Если всё же нужен обход через `general-purpose`, передать `model` из заголовка файла агента.
- `general-purpose` всегда запускать с явным `model`: без него агент наследует модель основного потока (обычно Opus). Механика и сбор (черновики по шаблону, правки по замечаниям ревью, выгрузки, чтение логов и страниц) — `sonnet`; Opus только там, где нужно суждение (ревью, разбор противоречий, архитектура).
- Границы фаз (сбор, решения, черновики или реализация, ревью, выкладка), контекст больше ~200K или пауза дольше часа: скилл `handoff` и новая сессия. Сессию с контекстом выше 300K не форкать и не продолжать «ещё одной задачей».

## Разработка и решения
- Репозиторий кода приложения (`<app>`) по умолчанию лежит рядом с этим: `<родитель корня репозитория>/<имя каталога>`. Имя каталога: TBD (задать при создании проекта). Если на машине он в другом месте — путь в `CLAUDE.local.md`. Основной поток определяет абсолютный путь (`git rev-parse --show-toplevel` и проверка, что каталог существует) и передаёт его агентам в брифе; абсолютные пути машины в файлы проекта не писать.
- Код приложения пишет только агент `app-developer` (sonnet; Opus через `model` — разово, на сложное место), ревью кода — `code-reviewer` (opus), которому передаются diff, требования, кейсы и ADR, но не отчёт разработчика. Замечания ревью — тому же разработчику через `SendMessage`; после двух кругов спор решает основной поток, а если он упирается в стори — пользователь.
- Отдельные сессии (`start_session`) для разработки не открывать без прямой просьбы пользователя: пользователь общается только с основным потоком, решения пользователя исполнителям передаёт только основной поток — со ссылкой на запись в конспекте.
- Вопросы пользователю — только его уровня и на языке продукта: «что важнее, X или Y, и что из этого увидит человек». Системный вопрос, который не решается из стори, — это пробел в стори: так его и формулировать, без технических вариантов.
- Системные решения, принятые без пользователя, — списком раз в этап и перед коммитом этапа (решение, опора, отброшенное); любое он может вернуть на обсуждение. Решение записывать в SR, ADR или конспект с пометкой «принял Claude, основание `PRJ-<n>`».
- Статусы `in-progress`, `acceptance`, `superseded`, приёмка и пересмотр требований — `docs/requirements/README.md`. На приёмке спорить доводами уровня пользователя (критерии стори, цель эпика, его NFR), SR — не довод.
- Работа над другим репозиторием, кроме кода приложения, — отдельной сессией в том репозитории, а не из этой.

# Compact instructions
При сжатии контекста сохранить: принятые решения и кто их принял; список изменённых файлов и их состояние; открытые и закрытые вопросы (номера, кем закрыты); ID требований и тестов (`PRJ-<n>`, `PRJ-T-<n>`), ключи внешних задач и ссылки на макеты; что ещё не сделано. Содержимое файлов не пересказывать: они на диске.
