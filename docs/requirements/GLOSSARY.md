# Глоссарий

Термины продукта и этой документации. Новые слова сначала сюда, потом в тикеты.

## Роли

Используются в формулировке user story: «Как \<роль\>…». Не отдельный справочник-атрибут — название роли должно совпадать со строкой ниже.

| Роль | Кто это |
|---|---|
| QA | проектирует кейсы, гоняет прогоны, заводит баги |
| разработчик | реализует SR, чинит баги, помечает кейс `automated` |
| автор требований | пишет эпики, стори и SR |
| релиз-менеджер | ведёт справочник релизов и решает, что входит в версию |

Новую роль — новая строка. В стори не выдумываем роли мимо таблицы.

## Артефакты требований

| Термин | Смысл |
|---|---|
| Epic | крупный кусок ценности; корень дерева |
| User story | сценарий роли; единица скоупа релиза |
| System requirement (SR) | атомарный SHALL; единица покрытия спецификации |
| NFR | Non-Functional Requirement: ограничение качества (скорость, надёжность, безопасность); покрывается так же, как SR. NFR пользователя — его условие на реализацию, обоснованное на уровне эпика или стори |
| ADR | Architecture Decision Record: запись одного крупного технического решения (варианты, выбор, обоснование, цена); лежит в `docs/adr/` репозитория кода; решает оркестратор, текст может написать `app-developer` по его указанию |
| Bug | дефект, найденный в прогоне; тикет, не строка результата |
| Идея | набросок внутри эпика, не отдельный артефакт |
| Оркестратор | основной поток Claude Code: ведёт диалог с пользователем, принимает системные решения, передаёт задачи агентам |
| Пакет приёмки | доказательства для `acceptance`: стенд, прогон сьюита стори, сценарий ручной проверки, список системных решений, журнал замечаний (`README.md`, «Приёмка») |
| Системное решение | решение уровня SR, NFR не от пользователя или ADR; принимает оркестратор, пользователь видит список раз в этап и может вернуть любое |

## Артефакты тестов

| Термин | Смысл |
|---|---|
| Test case | как проверять; библиотека в `docs/tests/cases/` |
| Test suite | набор кейсов для цели прогона; кейсами не владеет |
| Test run | конкретное исполнение набора; снимок состава |
| Test result | исход одного кейса в одном прогоне; ключ `(run, case)` |

## Справочники и идентификаторы

| Термин | Смысл |
|---|---|
| `PRJ-<n>` | ID тикета требований (эпик, стори, SR, NFR, баг) |
| `PRJ-T-<n>` | ID тестового артефакта (кейс, сьюит, прогон) |
| Release / `key` | версия поставки из справочника, не тикет |
| Environment / `key` | стенд или конфигурация из справочника |
| `revision` | commit репозитория на старте прогона (какие шаги кейсов действовали) |
| `build` | сборка продукта, который гоняли |

## Покрытие

| Термин | Смысл |
|---|---|
| Покрытие спецификации | есть утверждённый кейс с `verifies` на SR/NFR |
| Покрытие исполнением | статус кейса в completed-прогоне |
| Поставка | тикеты с ключом в `releases` / прогон с полем `release` |

Не путать три вопроса: «есть ли кейс», «прошёл ли прогон», «вошло ли в версию».
