# Требования

Хранение продуктовых требований в git: эпик → user story → системные требования.

Связи между артефактами, покрытие тестами и правила ссылок: [`TRACEABILITY.md`](TRACEABILITY.md). Термины: [`GLOSSARY.md`](GLOSSARY.md).

## Структура

```text
docs/requirements/
├── README.md
├── TRACEABILITY.md
├── GLOSSARY.md
├── _registry.md
├── _catalogs/
│   ├── releases.md
│   └── environments.md
├── _templates/
├── _canceled/              # отменённые до реализации, вне дерева; агенты не читают
│   └── PRJ-N-sr-....md
├── bugs/
│   └── PRJ-N-bug-....md
└── epics/
    └── PRJ-1-epic-.../
        ├── PRJ-1-epic-....md
        └── stories/
            └── PRJ-2-us-.../
                ├── PRJ-2-us-....md
                └── requirements/
                    ├── PRJ-3-sr-....md
                    └── PRJ-4-nfr-....md
```

Один артефакт — один файл. Иерархия дублируется папками.

Идея не отдельный тип: это короткий набросок внутри эпика (секция «Идея»).

Тесты **не** кладём в дерево требований. Каталог: [`docs/tests/`](../tests/README.md) — кейсы, сьюиты и прогоны. Их ID — `PRJ-T-<n>`, отдельный реестр. Покрытие спецификации — `verifies` на кейсе. Матрица: [`docs/tests/coverage-matrix.canvas.tsx`](../tests/coverage-matrix.canvas.tsx).

Релизы — справочник [`_catalogs/releases.md`](_catalogs/releases.md), не тикеты. В тикете поле `releases` (ключи из справочника). В прогоне — поле `release`.

Окружения — справочник [`_catalogs/environments.md`](_catalogs/environments.md). В прогоне и на баге — поле `environment`.

Баги — тикеты [`bugs/`](bugs/) (`PRJ-<n>-bug-…`), не строки результата и не узлы дерева эпик → стори.

## Идентификаторы

Два независимых счётчика:

| Пространство | Канонический ID | Реестр | Что нумерует |
|---|---|---|---|
| Требования | `PRJ-<n>` | [`_registry.md`](_registry.md) | epic, user-story, sr, nfr, bug |
| Тесты | `PRJ-T-<n>` | [`docs/tests/_registry.md`](../tests/_registry.md) | test-case, test-suite, test-run |

Справочники (`_catalogs/`) в счётчик не входят.

`PRJ-10` и `PRJ-T-10` — разные документы, это нормально.

Внутри каждого пространства номер **сквозной** по типам: нельзя два файла `PRJ-10` в требованиях и нельзя два `PRJ-T-10` в тестах. Номер не переиспользуется, даже если артефакт `obsolete`.

Имя файла и папки (требования):

```text
PRJ-<номер>-<тип>-<slug>.md
```

Пример: `PRJ-10-us-create-test-case.md`

| Тип | Код в имени | Значение `type` в YAML |
|---|---|---|
| Epic | `epic` | `epic` |
| User Story | `us` | `user-story` |
| System Requirement | `sr` | `system-requirement` |
| Non-functional | `nfr` | `nfr` |
| Bug | `bug` | `bug` |

Тестовые типы и имена — в [`docs/tests/README.md`](../tests/README.md).

В тексте и ссылках используем канонический ID (`PRJ-10` или `PRJ-T-10`). Тип и slug в имени можно менять; номер — нельзя.

Номера без ведущих нулей: `PRJ-10`, не `PRJ-010`.

## Внешние системы: поле `external`

Необязательное поле frontmatter у любого артефакта требований и тестов: ключ этого артефакта во внешней системе (трекер, вики, TMS).

```yaml
external:
  jira: ACME-123
  confluence: "4567890"
  testit: "1042"
```

- Ключ — имя системы латиницей в нижнем регистре (`jira`, `confluence`, `testit`), значение — ID в этой системе строкой.
- Один внешний ID принадлежит одному артефакту: два файла с одинаковым `external.jira` — ошибка.
- Поле пишет CLI интеграции при создании объекта во внешней системе (модули `optional/`) или человек вручную. Нет интеграции — поля нет.
- Источник правды — репозиторий. `external` не связь трассировки и не покрытие: во внешней системе может быть копия, но ID, `parent`, `links` и `verifies` живут здесь.

## Как выдать номер

1. Открыть реестр своего пространства (`docs/requirements/_registry.md` или `docs/tests/_registry.md`).
2. Взять значение **Next**.
3. Создать файл с этим номером.
4. Обновить реестр: `Last issued` = выданный номер, `Next` = `+1`.

## Статусы требований

Эпик и стори: `draft` → `review` → `approved` → `in-progress` → `acceptance` → `implemented` → `obsolete`
SR и NFR: `draft` → `review` → `approved` → `in-progress` → `implemented` → `obsolete` (без `acceptance`)

Окончания без релиза: `draft` | `review` | `approved` | `in-progress` → `canceled`; `approved` | `in-progress` | `acceptance` | `implemented` (релиз не вышел) → `superseded`.
| `approved` | утверждено: можно проектировать и реализовывать |
| `in-progress` | идёт реализация |
| `acceptance` | эпик или стори на приёмке у пользователя, см. «Приёмка» |
| `implemented` | SR и NFR: в коде есть, и это доказано (ревью кода, прогон кейсов, `implemented-in` на коммит). Эпик и стори: пользователь принял результат |
| `obsolete` | действовало в релизе, больше не действует; файл не удаляем, указываем чем заменено через `supersedes` |
| `superseded` | заменено до релиза: утверждено, возможно реализовано в коде, но в релиз не вышло; всегда со входящим `supersedes`, `releases` пустой, файл остаётся в дереве |
| `canceled` | решили не делать, замены нет; см. «Отменённые требования» |

`implemented` фиксирует проверенное состояние на коммите, а не «работает всегда»: сломалось позже — баг со связью `defects`, статус не откатывается. Вышло ли в релиз — по `releases` и статусу релиза в справочнике.

### Кто переводит статус

Пользователь решает на уровне эпика и стори и своих NFR (условия на реализацию, которые он сформулировал и обосновал). Системный уровень (SR, остальные NFR, ADR) ведёт основной поток (оркестратор) после независимого ревью.

NFR пользователя отмечены полем `decided_by: user` (у остальных NFR `decided_by: system` или поле пустое). Поле `owner` — ответственный человек, к этому не относится.

| Переход | Эпик, стори | NFR пользователя | SR, NFR системы |
|---|---|---|---|
| `review → approved` | пользователь | пользователь | оркестратор: `req-reviewer` без P0/P1, родительская стори не ниже `approved` (исключение — пересмотр стори) |
| `approved → in-progress` | оркестратор, когда первый ребёнок ушёл в `in-progress` | оркестратор, когда задача передана `app-developer` | то же |
| `in-progress → acceptance` | оркестратор: все `must`-дети `implemented`, пакет приёмки собран | — | — |
| `→ implemented` | пользователь, после приёмки | оркестратор, по тем же признакам, что SR; принимает пользователь вместе со стори | оркестратор: `code-reviewer` без P0/P1, кейсы с `verifies` прошли (инв. 25 `TRACEABILITY.md`), код закоммичен, есть `implemented-in` |
| `acceptance → in-progress` | пользователь не принял (дефект, ошибка вывода, пробел) | — | — |
| `acceptance → review` | пользователь: небольшой пересмотр, см. ниже | — | — |
| `→ superseded`, `→ canceled` | пользователь | пользователь | оркестратор, если это следует из решения пользователя по стори или из ревью — сообщает пользователю |

Кейсы (`docs/tests`) проверяют SR и NFR, поэтому их `review → approved` — тоже оркестратор после `req-reviewer`; кейсы на NFR пользователя — так же, сам NFR утверждает пользователь. ADR решает оркестратор, текст может написать `app-developer` по его указанию.

### Приёмка

Стори или эпик в `acceptance` ждут решения пользователя. Агенты отвечают за доказательства, пользователь — за решение. Пакет приёмки:

1. Поднятый стенд и инструкция в две-три строки: куда зайти, каким пользователем.
2. Прогон сьюита стори (`docs/tests/runs`, скилл `regression-report`): таблица «критерий приёмки → кейсы → статус» со скриншотами. Сьюит связан со стори через `relates-to`.
3. Сценарий ручной проверки: по каждому критерию приёмки — что сделать и что должен увидеть пользователь.
4. Список системных решений этапа, принятых без пользователя: любое из них он может вернуть на обсуждение.
5. Журнал замечаний приёмки: замечание → класс → ссылка → решение.

Приёмка эпика: все `must`-стори приняты, регрессионный прогон, проверка бизнес-цели эпика целиком.

Замечание пользователя на приёмке относят к одному из классов:

| Класс | Признак | Что делаем |
|---|---|---|
| Дефект | поведение расходится с критерием приёмки стори, целью эпика или NFR пользователя | баг (`defects`), исправление, повторный показ; стори остаётся в `acceptance` |
| Ошибка вывода | SR неверно передаёт критерий стори | дефект агента: SR исправляют, пересмотра требований нет |
| Пробел | требования не говорили, как надо; агент решил сам, пользователю не подходит | вето на системное решение: уточнение в стори или NFR, стори → `in-progress` |
| Изменение | сделано по утверждённому, но теперь нужно иначе | пересмотр требований, см. ниже |

Агент спорит только доводами уровня пользователя: критерии приёмки стори, цель и рамки эпика, NFR пользователя. SR — объяснение, как понят критерий, но не довод. Изменение не переклассифицируют в дефект, чтобы избежать спора: последнее слово за пользователем, но решение принимается с открытыми глазами.

### Пересмотр требований на приёмке

Сначала агент оценивает последствия: какие стори, SR, кейсы, код и решения конспекта затронуты, объём и риски. Решает вопрос «уйдёт ли текущий результат в релиз?»:

- **Да.** Стори → `implemented` (сделано по утверждённому). Изменение — новая стори в следующий релиз; её SR заменяют старые через `supersedes`, старые становятся `obsolete`, когда новые вышли в релиз (до этого старые действуют).
- **Нет, изменение небольшое.** Признак крупного: изменились роль или цель стори («Как … я хочу … чтобы …») или переписывается больше половины критериев. Небольшое: та же стори → `review`, критерий правится, пользователь утверждает заново; затронутые SR, ещё не `implemented`, правятся и проходят ревью; `implemented` SR не правятся — вместо них новые с `supersedes`, старые → `superseded`.
- **Нет, изменение крупное.** Старая стори и её переделываемые SR → `superseded`, `releases` очищается; новые создаются с `supersedes` и проходят путь заново. SR старой стори, которые изменение не затрагивает, переносят в новую стори (`parent`, папка, `children` обеих) с сохранением статуса; под `superseded`-стори живых детей не остаётся.

Какой это случай, решает пользователь (уровень стори), агент только предлагает оценку. Решение — в конспекте с пометкой «пересмотр решения от <дата>» и причиной. Утверждённые тексты молча не правят. Кейсы на заменённые требования → `obsolete`.

Приоритет: `must` | `should` | `could`.

### Отменённые требования

Требование, которое решили не делать и ничем не заменили, не `obsolete`: оно не действовало и в релиз не вышло. Отменить можно и из `in-progress`, когда код уже начат. Его отменяют так:

1. `status: canceled` и поле `cancel_reason` во frontmatter: одна строка — почему отменено и источник решения (конспект, кто решил). Из `in-progress` — плюс что сделать с написанным кодом (убрать задачей `app-developer` или оставить, если он нужен другим требованиям).
2. Файл переносят в `docs/requirements/_canceled/` (плоско, без дерева). `parent` остаётся для истории, `children` пустой.
3. Убирают его из `children` родителя и все ссылки на него из живых артефактов: `links`, критерии приёмки, обоснования, глоссарий, кейсы. Ссылки в конспектах и handoff — история, их не трогают.
4. Номер не переиспользуется.

Папка `_canceled/` исключена из поиска (`.ignore` в корне) и из чтения агентами (`CLAUDE.md`): отменённое не должно попадать в контекст при работе над действующими требованиями. Читать её — только по прямой просьбе пользователя. Линтер (`docs_lint.py`) проверяет: canceled только в `_canceled/` и с `cancel_reason`, в `_canceled/` только canceled, живые артефакты на canceled не ссылаются.

`releases`: список ключей из [`_catalogs/releases.md`](_catalogs/releases.md). Обычно заполняем на user story; на SR — если в версию идёт отдельное требование (хотфикс); на эпике — по желанию; на баге — Fix Version. Пустой список = ещё не запланировано в версию.

Статусы багов и тестов — в [`TRACEABILITY.md`](TRACEABILITY.md). Роли в стори — из [`GLOSSARY.md`](GLOSSARY.md).

## Как добавить артефакт

1. Выдать номер (см. выше).
2. Скопировать шаблон из `_templates/` в нужное место дерева.
3. Переименовать в `PRJ-<n>-<тип>-<slug>`.
4. Заполнить frontmatter и секции.
5. Прописать `parent` (кроме эпика и бага) и добавить себя в `children` родителя.
6. Ассоциации (`depends-on`, `constrains`, …) писать в `links` — см. [`TRACEABILITY.md`](TRACEABILITY.md).
7. Версию поставки и окружение выбирать из справочников, не создавать тикет релиза или окружения.
8. Роль в user story брать из [`GLOSSARY.md`](GLOSSARY.md).
